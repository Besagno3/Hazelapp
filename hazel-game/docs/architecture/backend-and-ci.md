# Database, CI, pull requests and deploys

> Moved verbatim out of `CLAUDE.md` on 2026-10-22 (it had grown to 9,000 lines). This is the full reference for the area — keep it accurate: when you change how this works, change it here in the same commit. `CLAUDE.md` holds only the rules that apply everywhere and a map to these files.

Covers: applying the schema and the migration rules, the CI jobs and SQL tests, and how pull requests, GitHub Actions and Vercel behave (drafts skip CI, `claude/**` branches never deploy).

## Database and CI

- DB schema lives in `supabase/migrations/` — apply with
  `supabase/apply_all_migrations.sql` (paste into the SQL Editor; generated by
  `npm run db:bundle`, replays every migration and records each in
  `supabase_migrations.schema_migrations`) or `supabase db push`.
  **Migration rules (#90):**
  1. **Forward-only.** Never edit a migration that has been applied anywhere
     (i.e. merged to `main`) — `supabase db push` skips recorded versions, so
     an edit silently never reaches those projects. Fix things in the next
     numbered file (see `0010_access_hardening.sql`).
  2. **Re-runnable.** The bundle replays everything on every run: `create
     table/index/schema if not exists`, `add column if not exists`,
     `create or replace function`, `drop policy|trigger if exists … on …`
     before `create policy|trigger`, grants/revokes (already idempotent).
  3. **No transaction control** (`begin`/`commit`) — the bundle wraps all of
     them in one transaction.
  4. After adding one: `npm run db:bundle`, and put a SQL test in
     `supabase/ci/*.test.sql` if it changes access rules.
  `db:bundle` refuses to build if rules 2–3 are broken; CI applies the bundle
  twice and runs the SQL tests.
- **CI** (`.github/workflows/ci.yml`, #81 + #88): job `test` = lint + bundle
  check + tests + `build:web` (what Vercel serves, #146; with placeholder
  `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` on that step only, so it
  bundles the real app — without them the app is dropped, #175); `edge-function` = `deno check`
  of both edge functions (generate-questions, delete-account) and the bank recheck script; `migrations` applies every migration to a plain
  Postgres (after `supabase/ci/supabase-stub.sql`) and runs
  `supabase/ci/*.test.sql` (`pin_limits_lock.test.sql` opens two more
  sessions with dblink to prove the PIN row lock; it commits its own family
  and deletes it again; `grown_ups_gate.test.sql` proves 👪 Grown-ups is held
  by the database, #167 — and fails when a `profiles` column is on neither
  side of the gate — and `grown_ups_password.test.sql` the password wait;
  `play_days.test.sql` the days-played rules, #29; `progress_history.test.sql`
  a day's play and `noted_play` (`noted: true`), the first day noted, topic
  starts, their days (`on`) and a corrected birth date's ages (0026,
  #169–#174, #181, #183 — it
  re-applies 0026 inside its own transaction with psql's `\ir`, to test the
  backfill and the bundle's replay over live data);
  the other tests that act as a grown-up open it first, on the stub's
  `request.jwt.claims` session). A new migration must apply cleanly there; put
  SQL-level tests for it in `supabase/ci/`.

## Pull requests — drafts skip CI

Open every PR as a draft. CI and Vercel previews skip drafts. Don't mark it
ready on your own; when the owner says merge, mark it ready, wait for every
check to go green (fix and push on red), then merge.

- **GitHub Actions:** every `ci.yml` job is gated on
  `github.event_name != 'pull_request' || !github.event.pull_request.draft`,
  and `pull_request` also triggers on `ready_for_review`, so marking a PR ready
  starts the full run. Drafts show grey "skipped" checks (a skipped required
  check still lets the PR merge). Pushes to `main` always run.
- **Vercel:** `vercel.json` → `ignoreCommand` runs
  `scripts/vercel-ignore-build.mjs`: production always builds; a preview builds
  only if its branch has an open, non-draft PR. Marking ready doesn't push, so
  the first preview builds on the next push. Uses `GITHUB_PR_READ_TOKEN`
  (Vercel, Preview env); any lookup failure fails open (builds).
- **What Vercel builds** (#146): `vercel.json` → `buildCommand` `npm run
  build:web`, `outputDirectory` `dist`: the public pages (`site/`) at `/` and
  the game at `/play/` (`/play` redirects there). A production build stops if
  `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` aren't set (#175): without
  them the game would ship with no app in it; previews only warn. The game is built with base
  `/` and only its page moves, so its root paths (`/sprites/…`, `/assets/…`)
  still work. A sign-in link or `?review` that lands on `/` is passed on to
  `/play/` by a script at the top of `site/index.html`.
- **`claude/**` branches never deploy on Vercel** (`vercel.json` →
  `git.deploymentEnabled`, #126): Vercel Hobby allows 100 deployments a day,
  and an ignored build still counts as a (cancelled) deployment, so the many
  pushes from Claude sessions used it up and blocked production. Those PRs get
  no Vercel preview; GitHub Actions still runs on them. Other branches keep
  the `ignoreCommand` rule above, and `main` always deploys.
- Dependabot / PRs opened as non-drafts run everything from the first push.
